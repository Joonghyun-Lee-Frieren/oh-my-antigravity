NEW / v1.1.0

Four focused surfaces carry the task from its first decisions to a reliable handoff. The existing edit guards, checks, and passed-file locks stay in place.

/oma-brief

Scope Brief

Record what should change, what should stay, and who owns each decision. Open questions and conflicting sources prevent the plan from being sealed.

/oma-design-check

Design Check

An independent auditor checks the exact plan before implementation. The auditor submits its own verdict; a changed plan needs a fresh check.

/oma-evidence

Evidence Window

Inspect the useful part of a long verification log without filling the conversation. Each bounded window includes integrity, position, and a next cursor.

/oma-checkpoint · /oma-resume

Session Trail

Preserve a compact handoff and compare it with current source when you return. Drift is explicit; an old snapshot never restores permission or clears locks.

Care scales with the scope: routine, elevated, and critical work use review caps of 120, 90, and 60 lines and repair batches of 3, 2, and 1. Sensitive paths can only raise care. Every profile retains real checks and independent receipts. Read the operating guide ↗

A boundary at every handoff.

01 / WORKFLOW

Procedures load when needed. Native capability limits and lifecycle hooks enforce the work that can happen in each phase.

01 / READ

Documentation first

A dedicated agent returns a short summary, sources, constraints, and unknowns. No writes or shell access.

02 / DESIGN

Seal the contract

Resolve Scope Brief decisions, seal exact files and checks, and obtain an independent Design Check. End the user turn.

03 / IMPLEMENT

Stay inside scope

The owning conversation applies patches. PreToolUse rejects off-scope edits, shell bypasses, and evidence writes.

04 / VERIFY

Prove each section

Actual check results and focused reviews determine completion. Stop locks passed files and schedules bounded repairs.

Design → implementation is a user-turn boundary. Repair batches use separate execution slices scheduled by Stop, with verification between batches.

Constraints the harness can enforce.

02 / GUARDS

Honest failure is a valid result. Missing evidence stays unknown, and a missing dependency can block the task.

PreToolUse

A narrow write surface

Exact planned paths, one conversation owner, protected state and logs, no arbitrary shell calls. Tests and fixtures need explicit scope.

Verification

Results from execution

Sealed argv checks record real exit codes, output, and source hashes. There is no agent command to declare a failed check passed.

Stop

Fix up to three

One batch contains at most three failed validators or non-passing sections. Every batch returns to verification before another is assigned.

Hash locks

Keep passed code stable

A file locks after its checks and every section pass. Further edits and stale evidence are rejected. Reopening requires operator recovery.

Section review

A small, concrete assignment

The hook builds one source section of up to 120 lines per reviewer. Receipts come from the reviewer’s own conversation. The parent cannot write PASS or steer its verdict.

Fail / unknown / blocked

No manufactured success

Do not fake service responses, skip validation, or invent logs. Bounded retries and explicit blockers stop unproductive repair loops.

Tool constraints complement runtime sandboxing. Trusted project validators and relevant behavioral reviews remain essential; pattern checks cannot prove arbitrary code is truthful. A repair unit may contain multiple diagnostics.

Current models. Explicit selection.

04 / UPGRADE

Moving from v1.0

Reinstall with agy plugin install. New plans require Scope Brief and native Design Check. Current clients must support child review messages and hooks.

Existing v1.0 sealed work can finish through its legacy path. New plans use native independent receipts; missing support remains unknown.
