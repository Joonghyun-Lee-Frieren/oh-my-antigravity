/oma-read · /oma-probe

Cover the source, including the tail

Register versioned snapshots, page every byte window, and record real CLI help. Missing source coverage or a failed required probe prevents handoff.

Read-only boundaries

Keep dependencies intact

Fingerprint declared dependency trees. Large-file writes need a planned rewrite; other edits target bounded existing chunks.

/oma-failure

An honest failure exit

Report DEPENDENCY_DEFECT with a real failed check, or name an external blocker. Preserve evidence and locks without inventing successful behavior.

AST + execution receipts

Check structure. Record execution.

Parse scoped Python for suspicious success shortcuts. Bind real status, output and source/input hashes to immutable receipts. Missing Python fails honestly.

/oma-repair-context

Fix related failures in order

Sealed dependency groups determine the next bounded batch. Real diagnostics are paged. A→B→A oscillation narrows focus to one group.

Blind section jury

Find the counterexample first

Markdown shards follow headings; each uses a fresh reviewer conversation. A central judge requires criterion-level evidence and vetoes unrequested nonmaterial demands.

01 / WORKFLOW

Procedures load when needed. Native capability limits and lifecycle hooks enforce the work that can happen in each phase.

01 / READ

Documentation first

Register and fully page source snapshots. A read-only reader returns constraints and unknowns. Required CLI probes use recorded execution.

02 / DESIGN

Seal the contract

Resolve Scope Brief decisions, seal exact files and checks, and obtain an independent Design Check. End the user turn.

03 / IMPLEMENT

Stay inside scope

The owning conversation applies patches. PreToolUse rejects off-scope edits, shell bypasses, and evidence writes.

04 / VERIFY

Prove each section

Real checks, AST results and blind reviews determine completion. Stop locks passed files and schedules dependency-ordered repairs.

Design → implementation is a user-turn boundary. Repair batches use separate execution slices scheduled by Stop, with verification between batches.

Constraints the harness can enforce.

02 / GUARDS

Honest failure is a valid result. Missing evidence stays unknown, and a missing dependency can block the task.

PreToolUse

A narrow write surface

Exact planned paths, one conversation owner, protected state and logs, no arbitrary shell calls. Tests and fixtures need explicit scope.

Verification

Results from execution

Sealed argv checks record real exit codes, output, and source hashes. There is no agent command to declare a failed check passed.

Stop

Fix up to three

A batch contains at most three dependency groups or non-passing sections. Sensitive scopes and detected oscillation use fewer. Every batch returns to verification.

Hash locks

Keep passed code stable

A file locks after its checks and every section pass. Further edits and stale evidence are rejected. Reopening requires operator recovery.

Section review

A small, concrete assignment

The hook builds one source section of up to 120 lines per reviewer. Receipts come from the reviewer’s own conversation. The parent cannot write PASS or steer its verdict.

Fail / unknown / blocked

No manufactured success

Do not fake service responses, skip validation, or invent logs. Bounded retries and explicit blockers stop unproductive repair loops.

Tool constraints complement runtime sandboxing. Trusted project validators and relevant behavioral reviews remain essential; pattern checks cannot prove arbitrary code is truthful. A repair unit may contain multiple diagnostics.

04 / UPGRADE

Moving from v1.0

Reinstall with agy plugin install. New plans require Scope Brief and native Design Check. Current clients must support child review messages and hooks.
